# Internationalization

The UI is bilingual with **Spanish as the default locale and English as the fallback**. `config/application.rb` sets the available locales, the default and the fallback chain; `rails-i18n` supplies the framework strings — dates, numbers, Active Record error messages — for both.

Locale is chosen per request in `ApplicationController`'s `switch_locale`: a `locale` cookie wins, then the browser's `Accept-Language` header through `locale_from_accept_language`, then Spanish. The cookie is written by `LocalesController#update`, which the language switcher (`app/views/shared/_locale_switcher.html.erb`) posts to. It stores only an available locale, and a stored locale the app no longer ships is ignored, so a forged or stale cookie falls through to the header. The switcher lists each locale by its own `locale_name` key, in its own language, and renders nothing when the app ships one locale. Adding a locale is adding it to `available_locales` and giving its file that key.

Rack's own `Rack::Request#accept_language` parses the header into language ranges with their q-values; the ranges are ordered by q-value (header order breaks ties), a range with `q=0` is dropped as not acceptable, and the first range whose primary subtag, lowercased, is an available locale wins, otherwise Spanish. Rack keeps a part with no language, such as `;q=1`, as an empty range; its primary subtag is the empty string, which matches no locale, so a malformed header falls back instead of failing the request. `ActionDispatch::Request#accept_language` returns the raw header string instead, which is why the controller builds a `Rack::Request` over the same env. The switch is an `around_action` wrapping the request in `I18n.with_locale`, never a bare assignment to `I18n.locale`, precisely so the global locale cannot leak across requests or across parallel test workers.

**No user-facing copy is hardcoded.** Everything goes through `t(...)` against `config/locales/es.yml` and `config/locales/en.yml`, which are kept in sync. Views use lazy lookups that resolve to the controller and action; shared partials and layouts use explicit keys; controllers translate flash messages; mailers translate subject and body. Adding copy means wrapping it in `t(".key")`, adding the key to BOTH files, and running `bin/i18n-tasks normalize`.

Two gates enforce it, in the same spirit as the coverage and accessibility gates. `raise_on_missing_translations` in `config/environments/test.rb` turns a missing key into a test failure, and the `i18n-tasks health` step in `config/ci.rb` fails on missing keys, unused keys and inconsistent interpolations. There is deliberately no static "hardcoded string in ERB" cop: no robust tool exists, since the available ones see only the Ruby inside ERB tags and flood false positives on literal HTML. The two gates plus review are the enforcement.

**Tests assert against translated keys, never against hardcoded copy** — system tests included, which resolve strings through `ApplicationSystemTestCase#t` against `BROWSER_LOCALE` (`test/application_system_test_case.rb`), the locale the browser actually renders, currently `:en`. Literals are acceptable only for HTML field names and ids and for data the test itself authored. This is not tidiness: a test written against English copy passes here and fails in an app that renders Spanish. The system suite runs in English because headless Chrome sends an English `Accept-Language`; the Spanish default path is covered by the unit and integration suites, which send no header at all, and by `test/integration/locale_detection_test.rb`. An app that pins the browser to a different locale changes that one constant, and every system test that goes through `#t` keeps working.

Translations are loaded eagerly on every prepare, through `config.to_prepare { I18n.eager_load! }` in `config/initializers/mission_control_jobs.rb`. The jobs dashboard swaps `I18n.config` for one whose only available locale is English, and the I18n backend loads its files lazily, dropping every locale that is not available at that moment. Without the eager load, the first translation looked up after boot or after a locale-file reload, if it happens inside `/jobs`, drops Spanish for the whole process: every page falls back to English until the next reload, and in the test suite a random worker renders English while its tests expect Spanish. `test/integration/mission_control_jobs_test.rb` reproduces it.
