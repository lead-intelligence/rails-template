# Superadmin panels

Every developer-only panel is gated by ONE shared HTTP basic-auth credential pair through `SuperadminAuthentication` (`app/controllers/concerns/superadmin_authentication.rb`), independent of the app's session auth. The concern's `included` block registers the `before_action`, so a controller only has to include it. Credentials resolve credentials-first then ENV on every request — `Rails.application.credentials.dig(:superadmin, :username)` and `:password`, falling back to `SUPERADMIN_USER` and `SUPERADMIN_PASSWORD` — and are compared with `ActiveSupport::SecurityUtils.secure_compare`. Each given half is cast with `to_s` before the comparison: a header whose decoded value has no colon gives Rails a nil password, and without the cast `secure_compare` raises and the request is a 500 instead of a `401`.

It is deny-by-default: when either half is blank every request gets a `401`. There is no "open when unconfigured" fallback anywhere, which is stricter than the Solid Errors and onlylogs gems' own defaults and is the reason each of those gems' built-in basic auth is switched off rather than configured.

Eight surfaces use it. `/errors` through `SolidErrors.base_controller_class` pointing at `SolidErrorsBaseController`; `/onlylogs` through `OnlylogsBaseController`; `/jobs` through `MissionControlJobsBaseController`, with `MissionControl::Jobs.http_basic_auth_enabled = false` in `config/initializers/mission_control_jobs.rb` so the gem's own gate no-ops; `/admin/feedbacks`, which also keeps `allow_unauthenticated_access` so only the superadmin gate applies; `/models`, the RubyLLM model list, for the same reason; `/madmin`; `/docs`, the documentation site, which keeps `allow_unauthenticated_access` for the same reason (see docs-site.md); and `/railspress/admin` through the `RailspressAdminAuth` concern, which is a per-app seam rather than a permanent choice (see blog.md).

`/madmin` is the madmin resource panel. `Madmin::ApplicationController` (`app/controllers/madmin/application_controller.rb`) includes the concern, and the panel runs under the strict N+1 gate like every other page. madmin's index view loads each row's `belongs_to` record on its own, so every resource controller whose index shows a `belongs_to` column overrides `scoped_resources` with `super.includes(...)`, the fix madmin's README documents (see `app/controllers/madmin/chats_controller.rb`). Without it a page of 20 rows runs 22 queries instead of 3, and the Bullet gate fails `test/integration/madmin_test.rb`. An index shows only madmin's default columns (the id, `title`, `name`, `user`, `created_at`) unless an attribute passes `index: true`; a `has_many` column opted in that way costs a `COUNT` per row that no `includes` removes. Dashboards exist for domain models only; the framework-internal and sensitive resources the generator produced were pruned from `config/routes/madmin.rb`, `app/madmin/resources/` and `app/controllers/madmin/`. madmin files are excluded from the coverage gate in `test/test_helper.rb`.

Adding a dashboard is `bin/rails g madmin:resource ModelName` **after** the model's migration has run, then pruning and routing as above. The generator reads the model's columns, so the table must already exist. There is deliberately no generator hook for this: `config.generators.after_generate` fires right after `rails g model`, before `db:migrate`, when the table does not exist yet — which is also why madmin ships no such feature. Keep the manual model, migrate, resource order.

`superadmin_authentication.rb` and `railspress_admin_auth.rb` are excluded from SimpleCov in `test/test_helper.rb`, because the RailsPress engine includes them into its admin controller at boot and Ruby's Coverage under parallel workers cannot attribute boot-loaded lines. Their behaviour is verified functionally instead, by each panel's integration test asserting 401 unconfigured and 200 with credentials.
