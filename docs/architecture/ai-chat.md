# AI chat

The app owns `Chat` (`acts_as_chat`) and `Message` (`acts_as_message`), scoped per user through `Current.user`. Since RubyLLM 2 the gem owns the rest: tool calls live in `ruby_llm_tool_calls` (read as `message.tool_calls`, a Hash of `RubyLLM::ToolCall` values), token usage and cost in `ruby_llm_usages`, and the model registry in `ruby_llm_models`. Once that table has a row RubyLLM stops reading its bundled JSON, so the table is seeded with the full registry (`db/seeds.rb`), as semantic-search.md explains. `ChatsController` creates a chat with its first prompt and `MessagesController` adds later turns; both call `Chat#add_message(role: :user, content:)`, the gem's own writer, and then enqueue `ChatResponseJob`. The new chat form offers `Chat.selectable_models`, the registry's own `chat_models.by_provider` filters over `Chat::PROVIDER`, and `ChatsController#create` accepts only a model from that same list: any other id, even one the registry knows, makes `find` raise `RubyLLM::ModelNotFoundError`, which `create` rescues to re-render the form with `422` and a `model` error, creating nothing. The job streams the assistant's reply into the message's content target, and only once the reply is persisted does it enqueue `GenerateChatTitleJob`, unless `chat.support?` — support conversations are never auto-titled — so titling can never run before there is a message to title. Titling asks for structured output through `RubyLLM.chat.with_schema(ChatTitleSchema)` (`app/schemas/chat_title_schema.rb`).

`Message#to_partial_path` and `#hidden_from_person?` ask each message whether it carries tool calls. Both `ChatsController#show` and `SupportChatsController#show` therefore load `@messages` with `.includes(:ruby_llm_tool_calls)`; without it the strict Bullet gate fails the moment a chat has more than one message.

`ChatsController#show` also renders tool results, and `MessagesHelper#tool_result_partial` reads each one's parent tool call, so it adds `:ruby_llm_parent_tool_call` to the `includes`; without it every tool result costs one query, and `test/controllers/chats_controller_test.rb` asserts the count does not grow with them. A chat without tool results leaves that preload unread, so `config/environments/test.rb` safelists it for Bullet. A support chat blanks tool results before reading the parent, so `SupportChatsController#show` does not preload it.

`ChatsController#index` lists chats with `includes(:model)` and a grouped `COUNT(messages.id) AS messages_count`, which `app/views/chats/_chat.html.erb` reads. Calling `messages.count` in the row instead runs one query per chat; `test/controllers/chats_controller_test.rb` asserts the query count does not grow with the number of chats.

The gem's `to_llm` rebuilds the whole history and preloads each message's tool calls, parent tool call, usage and attachments itself. A message with no usage or attachments leaves two of those preloads unread, so `config/environments/test.rb` safelists them for Bullet. `test/jobs/chat_response_job_test.rb` asserts the query count of a turn does not grow with the history.

`ChatResponseJob` declares Solid Queue's `limits_concurrency` with the chat id as key and a limit of one, so a second turn posted while a reply still streams waits blocked until the first job finishes. Two jobs on one chat at once would each load the history, each create an assistant message, and stream into each other's. The `duration` of 15 minutes is the failsafe after which a lock left by a dead worker is released; a reply that streams for longer lets the next turn start beside it.

Broadcasting is a set of hand-rolled synchronous callbacks on `Message` rather than the declarative `broadcasts_to`. The declarative helper's default renders the partial inside another job, and that render can land after the streamed chunks it is supposed to precede. The callbacks broadcast in the request or job that made the change, in order.

The update callback broadcasts an **append**, not a replace, and that is load-bearing. Action Cable hands a broadcast through two thread pools — the adapter's and the per-connection worker's — so two broadcasts about the same record can arrive in either order in every environment; RubyLLM's Rails guide at rubyllm.com/rails documents the hazard. Turbo's `append` removes an existing child with the same id before appending, so create-then-update and update-then-create both end with exactly one correct message element, whereas a replace that arrives before its create silently drops the reply. Appending on update would move a message to the end of the list, but the gem only ever updates the newest message, so the reordering is not observable.

`app/javascript/discard_stale_stream_updates.js` is the client half and inserts nothing. It listens for `turbo:before-stream-render` and calls `preventDefault` in exactly three cases: an append whose payload carries a `data-version` older than one already seen, an append aimed at a message that was removed (ids seen in a `remove` action are tombstoned), and a chunk aimed at a message the browser has already settled. When an append lands on an id that is already in the document it stamps `data-settled` on the incoming element, which is what makes the third case work. Everything else is rendered by Turbo itself.

`ChatResponseJob` broadcasts the streamed text at most once per `ChatResponseJob::STREAM_INTERVAL` (a tenth of a second). The first chunk goes out at once; later chunks collect until the interval has passed and then go out as one append. Each broadcast is one row in the Solid Cable database and one Turbo render in the browser, so a reply of 500 chunks costs about 90 of each instead of 500, and the production cable adapter polls at the same tenth of a second, so the person sees no difference. Text still waiting when the reply ends, or when the gem moves on to the next message of a tool call, is dropped on purpose: the update broadcast of that message carries its full content. `test/jobs/chat_response_job_test.rb` asserts the bound and the exact final content.

When the provider fails, `ChatResponseJob` rescues `RubyLLM::Error` around `chat.complete` only, broadcasts the `messages/failure` partial into the conversation and re-raises so Solid Errors records it. There is no `retry_on`: Solid Queue performs no automatic retries, so a retry declaration would only be honoured in environments that do, and the person would see the failure bubble once per attempt. Titling is outside the rescue on purpose — a failed title must not look like a failed answer.

A chat deleted before its jobs run discards them instead of failing them. `ChatResponseJob` takes the chat id, not the record, so it declares `discard_on ActiveRecord::RecordNotFound`; `GenerateChatTitleJob` takes the record and is discarded by `ApplicationJob`'s `discard_on ActiveJob::DeserializationError`. Without them every deleted chat leaves a job in the failed-executions table forever.

Daily volume is capped per person, not per chat. `User::DAILY_MESSAGE_LIMIT` is the number of user messages allowed in a calendar day, `User#messages_remaining_today` computes what is left from `User#messages_sent_today`, and `ApplicationController#ensure_within_quota` refuses `ChatsController#create` and `MessagesController#create` with `403` once it reaches zero. The composer partial reads the same method to show the remaining count and to replace the form with the exhausted notice, so the number the person reads and the number enforced are the same one. `MessagesController` additionally rate-limits bursts to 20 messages a minute per user.

The quota count is served by the `messages` index on `chat_id, role, created_at`. The table has no index on `role` alone: SQLite has no statistics to weigh two candidate indexes and picks the `role` one, which scans every person's user messages; `test/models/user_test.rb` asserts the query plan.

The app configures one provider, so the form lists about 130 models instead of the registry's nearly 1,500 chat models, and the page is a sixth of the size. The gem's `chat_models` filter goes by the registry's model type, which also classes OpenAI's speech and transcription models as chat models, so the list includes them.

`/models` lists every chat model RubyLLM knows about, of every provider, and can refresh them from the provider. It is a developer view, so `ModelsController` includes `SuperadminAuthentication` and skips session auth; see superadmin-panels.md.

The move from RubyLLM 1.16 to 2.1 is four generated migrations plus one of ours. `PrepareRubyLlmV2Upgrade`, `BackfillRubyLlmV2Data` and `FinishRubyLlmV2Upgrade` come from the 2.0 gem's `ruby_llm:upgrade` in its default rename mode: `models` and `tool_calls` become `ruby_llm_models` and `ruby_llm_tool_calls`, and the token columns of each reply become rows in `ruby_llm_usages`. 2.1 no longer ships the `LegacyContentSQL` helper the backfill required, so the backfill carries its own copy and a fresh `bin/rails db:migrate` still runs. The four generated files stay out of RuboCop (`.rubocop.yml`) so they can be read against the gem's templates. `UpgradeRubyLlmTo21` comes from the 2.1 gem's generator. The old columns (`messages.model_id`, `tool_call_id`, `content_raw` and the token counts) stay until the gem's cleanup phase, which only the 2.0 generator writes (`--phase cleanup`) and which cannot be undone, so an app with real conversations runs it once it trusts the upgrade. `DropForeignKeysFromLegacyMessageColumns` removes the foreign keys those old columns kept: nothing maintains them any more, and deleting a chat with tool calls from before the upgrade failed on them. The initializer keeps OpenAI on Chat Completions (`config.openai_protocol = :chat_completions`), the wire the test stubs speak; 2.x defaults to the Responses API.
