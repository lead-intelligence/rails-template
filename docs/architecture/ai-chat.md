# AI chat

The chat models are RubyLLM's generated `acts_as_chat` set — `Chat`, `Message`, `ToolCall`, `Model` — scoped per user through `Current.user`. `Model` is also the gem's model registry: once the `models` table has a row RubyLLM stops reading its bundled JSON, so the table must be seeded with the full registry (`db/seeds.rb`), as semantic-search.md explains. `ChatsController` creates a chat with its first prompt and `MessagesController` adds later turns; both call `Chat#create_user_message`, the gem's own writer, and then enqueue `ChatResponseJob`. The job streams the assistant's reply, appending each chunk to the message's content target, and only once the reply is persisted does it enqueue `GenerateChatTitleJob`, unless `chat.support?` — support conversations are never auto-titled — so titling can never run before there is a message to title. Titling asks for structured output through `RubyLLM.chat.with_schema(ChatTitleSchema)` (`app/schemas/chat_title_schema.rb`).

`Message#to_partial_path` and `#hidden_from_person?` build a full `to_llm` representation of each message, touching its tool calls, parent tool call, model and attachments. Both `ChatsController#show` and `SupportChatsController#show` therefore load `@messages` with `.includes(:tool_calls, :parent_tool_call, :model, attachments_attachments: :blob)`; without it the strict Bullet gate fails the moment a chat has more than one message.

The gem's `to_llm` rebuilds the whole history the same way and loads `messages` with no preloading, so `Chat#to_llm` preloads those four associations first, unless the messages are already loaded. Without it `ChatResponseJob` runs two queries per message of history on every turn; `test/jobs/chat_response_job_test.rb` asserts the query count does not grow with the history.

Broadcasting is a set of hand-rolled synchronous callbacks on `Message` rather than the declarative `broadcasts_to`. The declarative helper's default renders the partial inside another job, and that render can land after the streamed chunks it is supposed to precede. The callbacks broadcast in the request or job that made the change, in order.

The update callback broadcasts an **append**, not a replace, and that is load-bearing. Action Cable hands a broadcast through two thread pools — the adapter's and the per-connection worker's — so two broadcasts about the same record can arrive in either order in every environment; RubyLLM's Rails guide at rubyllm.com/rails documents the hazard. Turbo's `append` removes an existing child with the same id before appending, so create-then-update and update-then-create both end with exactly one correct message element, whereas a replace that arrives before its create silently drops the reply. Appending on update would move a message to the end of the list, but the gem only ever updates the newest message, so the reordering is not observable.

`app/javascript/discard_stale_stream_updates.js` is the client half and inserts nothing. It listens for `turbo:before-stream-render` and calls `preventDefault` in exactly three cases: an append whose payload carries a `data-version` older than one already seen, an append aimed at a message that was removed (ids seen in a `remove` action are tombstoned), and a chunk aimed at a message the browser has already settled. When an append lands on an id that is already in the document it stamps `data-settled` on the incoming element, which is what makes the third case work. Everything else is rendered by Turbo itself.

When the provider fails, `ChatResponseJob` rescues `RubyLLM::Error` around `chat.complete` only, broadcasts the `messages/failure` partial into the conversation and re-raises so Solid Errors records it. There is no `retry_on`: Solid Queue performs no automatic retries, so a retry declaration would only be honoured in environments that do, and the person would see the failure bubble once per attempt. Titling is outside the rescue on purpose — a failed title must not look like a failed answer.

Daily volume is capped per person, not per chat. `User::DAILY_MESSAGE_LIMIT` is the number of user messages allowed in a calendar day, `User#messages_remaining_today` computes what is left from `User#messages_sent_today`, and `ApplicationController#ensure_within_quota` refuses `ChatsController#create` and `MessagesController#create` with `403` once it reaches zero. The composer partial reads the same method to show the remaining count and to replace the form with the exhausted notice, so the number the person reads and the number enforced are the same one. `MessagesController` additionally rate-limits bursts to 20 messages a minute per user.

The quota count is served by the `messages` index on `chat_id, role, created_at`. The table has no index on `role` alone: SQLite has no statistics to weigh two candidate indexes and picks the `role` one, which scans every person's user messages; `test/models/user_test.rb` asserts the query plan.

`/models` lists the chat models RubyLLM knows about and can refresh them from the provider. It is a developer view, so `ModelsController` includes `SuperadminAuthentication` and skips session auth; see superadmin-panels.md.
