# Notifications

noticed's install migrations create `noticed_events` — the thing that happened, with an optional polymorphic record — and `noticed_notifications`, one row per recipient with `read_at` and `seen_at`, both in the primary database. `User` declares `has_many :notifications, as: :recipient, dependent: :destroy`.

The installed version keeps the event/notification split, which means database persistence is core rather than a delivery method. `deliver_by :database` is deprecated and does nothing; `SomeNotifier.deliver(recipients)` always saves synchronously inside a transaction and then unconditionally enqueues `Noticed::EventJob`. Only declared delivery methods — email, Action Cable and so on — actually do anything in that job, so a notifier with none still enqueues a job that does nothing.

`ApplicationNotifier < Noticed::Event` (`app/notifiers/application_notifier.rb`) is the only notifier code in `app/`; **the app ships zero notifiers**, the same capability-only stance as pundit and analytics. The navbar bell (`app/views/shared/_notification_bell.html.erb`, `app/helpers/notifications_helper.rb`) and `/notifications` (`NotificationsController`, scoped through `Current.user`) render whatever `message` a notifier's notification methods define.

`TestNotifier` in `test/notifiers/` is the only notifier in the repository. It is required by a glob in `test/test_helper.rb`, is never loaded by app code, and exercises the whole pipeline — deliver, persist, unread count, mark read — plus the opt-in email pattern, so the wiring is covered without deciding for the app what it should notify about. Its notifications carry a `belongs_to :event`, and eager-loading it in the pipeline test needed a narrow Bullet safelist (`Bullet.add_safelist type: :unused_eager_loading, class_name: "TestNotifier::Notification", association: :event`, `config/environments/test.rb`) — a verified false positive, narrowed to that one class and association rather than widening the rule.

The one delivery method that ships is `app/notifiers/delivery_methods/push_native.rb`, which pushes a notifier's title, body, path and badge to the recipient's native devices through `action_push_native`; the mobile page (`mobile.md`) explains how those devices get registered.

The bell runs on every signed-in page, and noticed's install migration indexes `noticed_notifications` by recipient only, so its unread count and its newest five read every notification the person has ever received. Two indexes of the app's own serve it: recipient plus `created_at` gives the newest in order without a sort, and recipient plus `read_at` counts the unread ones from the index alone. With 20,000 notifications a page took about 3.2 ms, 1.7 ms of it in those two queries; with the indexes it takes about 1.5 ms. Nothing purges old notifications, so without them that cost grows with every one delivered. `test/helpers/notifications_helper_test.rb` asserts both query plans.

`/notifications` is paginated (see pagination.md), `NotificationsController::PER_PAGE` at a time. The controller loads the page once, so the view's empty-state check reads the loaded records instead of asking the database again. The "mark all read" button reads `unread_notifications_count`, the memoized helper the navbar bell already calls, because it marks every unread notification and not only the ones on the page; checking the page's records would hide it while older pages still hold unread ones.

Adding a notifier is `bin/rails generate noticed:notifier NewCommentNotifier`, or a class by hand under `app/notifiers/` that inherits from `ApplicationNotifier`. Its `notification_methods` block defines `message`, which the bell and the list render and which every notifier needs, and optionally `url`. Delivery is `NewCommentNotifier.with(record: comment, comment: comment).deliver(post.author)`. The `record:` parameter fills the event's polymorphic `record`, so every notification about one comment can be found later; any other parameter is read inside the notifier through `params`. A recipient reads its inbox with `notifications.unread.count`, `notifications.newest_first` and `mark_as_read`.

`User#notifications` cleans up the recipient side only. When a notifier passes `record:` and that record is destroyed later, its events and their notifications stay in `noticed_events`. The model behind `record:` therefore declares `has_many :noticed_events, as: :record, dependent: :destroy, class_name: "Noticed::Event"`, as noticed's own README documents under "Associating Notifications".

Email is opt-in per notifier and never on by default. A `deliver_by :email` block sets `config.mailer` and `config.method`, both required by `Noticed::DeliveryMethods::Email`; the delivery method calls `mailer.with(params).public_send(method)`, so the mailer action reads `params[:notification]`, `params[:record]` and `params[:recipient]`. `config.if` and `config.unless` are evaluated per recipient at delivery time, not when `deliver` is called, so they can read a per-person preference. `TestNotifier` exercises exactly that shape with a plain mailer, and `test/notifiers/test_notifier_test.rb` delivers with and without the opt-in. In development the mail lands in the `/letter_opener` inbox (see email.md).

Browser web push is not installed: it needs the web-push gem, VAPID keys and a service-worker subscription flow, added when a real notifier needs it. Native phones are covered by the push delivery method above; noticed's own `:fcm` and `:ios` delivery methods also exist and need only credentials and device tokens.
