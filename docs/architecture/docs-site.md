# Documentation site

`/docs` serves this repository's own documentation as a site: the two guides (README.md and CLAUDE.md) and every architecture page, rendered from Markdown with a landing page, a sidebar, a table of contents, a light/dark control and a ⌘K search. It is the eighth surface behind the shared superadmin basic auth (see superadmin-panels.md), so it is deny-by-default like the rest — `DocsController` (`app/controllers/docs_controller.rb`) includes the concern and keeps `allow_unauthenticated_access`, so only the superadmin gate applies. `app/views/sitemaps/robots.text.erb` disallows it and its own layout sends `noindex`. The `Dockerfile` copies the whole tree and `.dockerignore` keeps the documentation in, so `/docs` works in production too.

`Doc` (`app/models/doc.rb`) is a plain object, not a record. `Doc.all` returns the two guides followed by every architecture page in alphabetical order; a page's slug is its path with the leading directory and the `.md` extension removed, so the architecture pages live under `/docs/architecture/…`. Nothing else in the tree is readable: the superpowers directory is deliberately outside the list, because it is template-only and a child app does not have it. `Doc#title` parses an architecture page's own `# ` heading, but README.md and CLAUDE.md both start with the app's name, so the two guides are special-cased to the i18n keys under `docs.guides` instead — the app name never leaks into the cards, the sidebar or the page `<title>`.

`Doc.find` resolves a slug by matching it against that list rather than by joining it onto a root path. Path traversal is therefore impossible by construction instead of by sanitising the parameter — a slug that is not one of the listed pages raises `ActiveRecord::RecordNotFound` and the request is a 404, and no reachable code path ever turns a request parameter into a filename.

Rendering is Redcarpet, declared explicitly in the `Gemfile` although the blog engine already depends on it. `Doc.markdown` renders with `filter_html`, so raw HTML inside a page is dropped, and the view sanitises the result a second time through `DocsHelper::DOC_TAGS` and `DOC_ATTRIBUTES` (`app/helpers/docs_helper.rb`). That allow-list keeps `id`, which is what makes the heading anchors survive sanitisation — dropping it would leave every table-of-contents link pointing at nothing. `Doc::Renderer#link` and `#codespan` are Ruby overrides, so they never run through Redcarpet's own C-level scheme check; the view's `sanitize` call is the only thing that strips a `javascript:` or `data:` href before it reaches the browser.

`Doc.markdown`, `Doc.table_of_contents` and `Doc.plain_text` build a new Redcarpet parser on every call. A `Redcarpet::Markdown` keeps its work buffers inside the object, and the Ruby callbacks of `Doc::Renderer` let Puma switch threads in the middle of a render, so two requests that share one parser trip a C assertion and abort the whole server process.

`Doc::Renderer` overrides Redcarpet's `link` and `codespan` callbacks so that a reference to another page becomes a link into `/docs`, whether it is written as a Markdown link or, as this repository writes them, as a backticked file name. Anything else is left exactly as it was, so a backticked source path stays a code span. Overriding a callback means writing the whole element: the built-in renderers are implemented in C and define no Ruby method to call `super` on.

Heading anchors come from Redcarpet's `HTML_TOC` renderer, never from a hand-rolled slug of the `##` lines. Both renderers compute the anchor with the same C function, so parsing the table of contents the library produces is the only way to be sure the anchor matches the `id` the page actually carries; a separate slugifier drifts the first time a heading contains punctuation, and every link in the table of contents silently goes nowhere. The table of contents covers level-two headings only, so a page written as a single narrative has none and the column is not rendered.

The search index is embedded as a `<script type="application/json">` data island built by `Doc.search_index`, escaped by `DocsHelper#docs_search_index`, and read by `docs_search_controller.js`. Each entry carries its page's title, heading text and a `StripDown`-rendered plain-text body; a query is matched against title and heading first, and only falls back to the body — shown as a short snippet built with `textContent` — when neither matches, so a page about an unrelated topic never outranks the page whose heading actually names the thing being searched for. The Content Security Policy is nonce-based and strict for scripts (see security-headers.md); a JSON block is never executed, so it needs no nonce, whereas an inline script assigning the index to a variable would be blocked and the search would fail silently with nothing in the console for the person looking at it.

`Doc` keeps two in-process memos. The page list behind `Doc.all` and `Doc.route` is keyed on the modification time of the architecture directory, which changes when a page is added, removed or renamed, so the directory is globbed once per change rather than once for every link a page renders. The search index JSON is keyed on the locale and on every page's path and modification time, so an edited page shows up on the next request in development while production builds it once per locale. A key without the locale would serve one language's guide titles to the other.

`Doc.root` is the directory everything is read from. It is `Rails.root`; the model test points it at a temporary tree to prove that an edited and an added page invalidate both memos, because adding a real page under the architecture directory would break the documentation test running in a parallel worker.

The light/dark control is DaisyUI's `theme-controller` input, and `docs_theme_controller.js` only restores a stored choice by checking the matching radio — it never writes a theme onto the root element. With neither radio checked the page follows the browser's colour-scheme preference, which is exactly what the accessibility gate emulates when it audits every page in both schemes.

Prose styling is about a hundred lines of `@layer components` in `app/assets/tailwind/application.css`, keyed on `.docs` and written against DaisyUI tokens, because no typography plugin is vendored. Links there are underlined in the primary colour rather than coloured with it: the primary token does not reach the required contrast ratio against the page background in the dark theme, and every accessibility audit of a page full of links fails on it.

The topbar's menu control (`app/views/docs/_topbar.html.erb`) is a `<label>` for the drawer checkbox, and it names itself with an `sr-only` span, never `aria-label`. A label has no role that permits `aria-label`, so axe reports `aria-prohibited-attr` whenever the label is rendered: below the `lg` breakpoint, and on any page audited before its stylesheet applies, which is how the attribute once failed the suite intermittently at desktop width. The search button's text uses `sr-only sm:not-sr-only` for the same reason — hidden with `hidden`, a narrow screen leaves the button with no name. The narrow-screen case in `test/system/docs_test.rb` audits that state.

Code blocks wrap instead of scrolling sideways. A `pre` that scrolls horizontally is a scrollable region a keyboard cannot reach, which axe reports on any screen narrow enough for a line to overflow.

`layouts/docs.html.erb` is a layout of its own, so the application navbar, the flash and the support widget stay out of the documentation. The sidebar arrives through `content_for :sidebar`, which is what distinguishes a page (drawer plus sidebar) from the landing (hero plus cards) without a second layout.
