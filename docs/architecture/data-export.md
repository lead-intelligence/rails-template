# Data export

The right-to-portability pair of account deletion. From the "Your data" card on `/profile` a signed-in person posts to `DataExportsController#create`, which enqueues `DataExportJob` and redirects with a "we will email you" notice. The job builds a ZIP through `DataExport` (`app/models/data_export.rb`), attaches it to `User#data_export` — a `has_one_attached`, so no migration of its own — and mails `DataExportMailer.ready`. `create` is rate limited per person to `DataExport::REQUEST_LIMIT` requests per `DataExport::REQUEST_WINDOW`, because each request queues a job that reads the person's whole account; the refusal message interpolates the limit. That email links to `GET /data_export`, which requires a signed-in session and streams the attachment; it deliberately does not carry a signed blob URL, because a ZIP of someone's entire account must not hang off a link that can be forwarded.

What goes in is derived, not listed. `DataExport` walks the `dependent: :destroy` associations of `User` and then, recursively, of every model it reaches — exactly the set the deletion cascade erases, so "what is erased" and "what is exported" cannot drift apart — and drops the framework-internal reflections that `has_one_attached` and `has_rich_text` declare behind the scenes. Each level is one relation built as a subquery of its parent, so a chat's messages and their tool calls cost one query each, not one per chat. `data.json` keys each list by its association path: `chats`, `chats/messages`, `chats/messages/tool_calls`, `ahoy_visits/events`.

A record that two cascades erase is exported under both paths. An analytics event belongs to the person and to their visit, so it appears in `ahoy_events` and in `ahoy_visits/events`.

`DataExport::RECORD_SCOPES` narrows a model to the rows the person may see. `Message` goes through `Message.visible_to_person`, which drops the system, tool-call and tool-result messages of support chats — the same set `Message#to_partial_path` blanks — so the export cannot leak what the support chat's binding rule hides. The tool calls under those messages drop out with them, because the next level is built from the narrowed relation.

Each record is serialized with `as_json`, minus the columns in `DataExport::EXCLUDED_COLUMNS`: `User`'s `password_digest`, because a password hash must never leave the app even to its owner, `Document`'s `embedding`, because 1536 floats are noise to a human, and `Message`'s `content_raw` and `thinking_signature`, because they are opaque provider payloads. Attachments are collected generically into `files/<association path>/<id>/<name>/<attachment id>/<filename>` — the attachment id keeps two files with the same name on one record from overwriting each other — excluding the export attachment itself so exports never nest. Adding a model with `dependent: :destroy` on `User`, or on anything below it, therefore adds it to both deletion and export automatically; trimming it means extending `EXCLUDED_COLUMNS`, `EXCLUDED_ATTACHMENTS` or `RECORD_SCOPES`.

The ZIP never sits in memory. `DataExport#write` streams into any seekable IO, and `DataExportJob` hands it a `Tempfile` and attaches that file. Each blob is downloaded in chunks straight into its entry, and attachment entries are STORED rather than deflated, because photos are already compressed and deflating them again costs time for no gain. Attachments are looked up with one query per association, and an association whose model declares no attachments is skipped, so the query count stays flat however many records a person has. `test/models/data_export_test.rb` pins that count.

A blob whose file is gone from storage is skipped, not fatal. `DataExport#write` asks the service whether each file exists before it opens the entry, leaves the missing ones out and lists their would-be paths under `missing_files` in `data.json`, which is written last for that reason. Without the check one lost file would raise `ActiveStorage::FileNotFoundError` on every attempt, and nothing retries the job, so the person could never export again.

Active Record Encryption decrypts transparently on read and `as_json` reads through it, so an `encrypts`'d column is exported in PLAINTEXT — correct for portability, since the person gets readable data back.

One consequence: a genuinely secret encrypted field (an API token, a TOTP secret) has to be added to `EXCLUDED_COLUMNS` exactly like `password_digest`, or it leaves the app in the clear inside someone's downloaded ZIP.

The other consequence: the generated ZIP is itself decrypted at rest, so it cannot be left to linger on disk (the retention paragraph below is what stops that). `test/models/data_export_test.rb` pins the plaintext behaviour with a probe column, configuring explicit keys so it runs where no master key exists. No domain model in the tree declares `encrypts` today.

Because the ZIP is decrypted at rest it is not allowed to linger. `DataExport::RETENTION` is 48 hours; `DataExportsController#show` refuses to serve an older export, purges it and shows `data_exports.show.expired`, and the `purge_expired_data_exports` task in `config/recurring.yml` sweeps expired export attachments hourly in production.

Action Text rich text is included as text. `DataExport` detects `has_rich_text` associations generically and adds each one's `to_plain_text` under its attribute name, eager-loading them so walking many records does not trip the Bullet gate. `to_plain_text` rather than `to_html` is deliberate: it renders no attachment partials, so it is safe in a job with no view or URL context. The limitation that follows is that formatting and files embedded in the rich-text record itself are not in the ZIP — only the text.
