# Auth

Native Rails authentication lives in `app/controllers/concerns/authentication.rb` (session resume, `require_authentication`, `allow_unauthenticated_access`, `start_new_session_for`, `terminate_session`) with `SessionsController`, `RegistrationsController`, `ProfilesController`, `EmailConfirmationsController`, `EmailChangesController` and `ActiveSessionsController` on top. `Current.user` (`app/models/current.rb`) is the only scope every other controller trusts. Avatars are Active Storage variants on `User#avatar` (`thumb`, `medium`) with an initials fallback from `User#initials`. There is no 2FA out of the box; the last paragraph sketches the path.

A session cookie whose `Session` row is gone — revoked from another device, or the account deleted — is looked up once per request and then deleted. `find_session_by_cookie` remembers that it already checked, because `Current.session ||=` cannot memoize a nil, and `authenticated?` is called several times by the layout; without the flag each call repeats the same query on every page.

`request_authentication` remembers the URL that asked for a sign-in only for a `GET`, and `after_authentication_url` returns there, else to the root. The redirect after sign-in is always a `GET`, so a remembered form submission, such as a "mark all read" sent after the session expired, would land on a route with no `GET` and answer `404`.

Signup creates an unconfirmed user and sign-in is blocked until the address is confirmed. `RegistrationsController#create` saves the user with `users.confirmed_at` nil, mails `EmailConfirmationsMailer.confirm` and redirects to sign-in with a "check your email" notice; `SessionsController#create` refuses a user that is not `confirmed?` with the `sessions.create.unconfirmed` alert. The confirmation link is `GET /email_confirmations/:token`, whose token comes from `User.generates_token_for :email_confirmation` over the email address itself, so changing the address invalidates any outstanding link; it expires after `User::EMAIL_CONFIRMATION_EXPIRES_IN`. To relax this to "allow sign-in but mark unconfirmed", change the `user.confirmed?` guard in `SessionsController#create` — nothing else depends on it.

The `test/fixtures/users.yml` rows set `confirmed_at` for exactly this reason: a fixture without it cannot sign in and every controller/system test that authenticates as a fixture user would fail at the sign-in step, not at whatever it meant to test.

Resending a confirmation is `GET /email_confirmations/new` plus `POST /email_confirmations`. It only mails an address that exists and is still unconfirmed, but it always redirects with the same notice, so the endpoint never reveals whether an account exists. Accounts that are never confirmed do not accumulate: `User.purge_unconfirmed` destroys unconfirmed users older than `User::UNCONFIRMED_RETENTION` and runs daily from `config/recurring.yml`.

Password reset is `resources :passwords, param: :token` (`config/routes.rb`) and `PasswordsController` (`allow_unauthenticated_access`). `#create` looks up the address and, only when it exists, sends `PasswordsMailer.reset`, but redirects to sign-in with the same notice either way — like resend, it never reveals whether an account exists. The link resolves through `User.find_by_password_reset_token!`, the finder `has_secure_password` generates for free from `generates_token_for :password_reset, expires_in: 15.minutes`; a missing, tampered or expired token raises `ActiveSupport::MessageVerifier::InvalidSignature`, which `#set_user_by_token` rescues into a redirect back to the request form. `#update` sets the new password and destroys every one of the user's sessions — unlike a password change from `/profile`, which keeps the current session alive.

`#update` rejects a blank password before saving, with the `passwords.update.alert` alert. `has_secure_password` silently ignores an empty password, so without that guard the save would succeed, report success and sign out every device while the old password and the token both stay valid.

Rate limits guard every unauthenticated credential endpoint, using Rails' own `rate_limit` on the controller: sign-in, confirmation resend and password-reset requests all allow 10 attempts per 3 minutes, signup 10 per hour. Each limit redirects with its own i18n alert instead of raising. Profile updates are a separate, authenticated limit — 5 per 5 minutes keyed by `Current.user.id` rather than by IP, because the endpoint already requires a session and IP keying would punish everyone behind one NAT.

Changing an email address or a password from `/profile` requires the current password. `User` validates `password_challenge` on the `:profile` validation context whenever credentials are changing, and `ProfilesController#update` saves with `save(context: :profile)`; `profile_params` drops blank password fields so a plain name-or-avatar edit does not demand one. A new address is parked in `users.unconfirmed_email` and only becomes the real address when the person clicks the link mailed by `EmailConfirmationsMailer.change`, which `EmailChangesController#show` resolves through `User.confirm_email_change`.

A pending address that another account already owns fails the `:profile` context with the standard `:taken` error, so `ProfilesController#update` re-renders the form and mails nothing. The check runs whenever a pending address is present, not only when it changes, so re-submitting an address someone else has claimed since does not mail that person either. `users.email_address` is unique, so such a change could never be confirmed anyway; without the check the only effect would be a confirmation mail in a stranger's inbox.

The pending address is cancellable by submitting a blank one and resendable by submitting the same one again, because the mail is gated on the submitted parameter rather than on the dirty flag — a plain re-submit of the identical address still mails a fresh confirmation. The mail is built when its job runs, from the address pending at that moment, so a change cancelled before then sends nothing: `EmailConfirmationsMailer#change` returns without calling `mail`, and a mail with no recipient would otherwise fail the job.

One consequence of the `:profile` context: a future validation declared `on: :update` will not run on this path, since `save(context: :profile)` only runs validations scoped to `:profile` (plus the context-less ones).

A successful password change signs out every other device — `ProfilesController#update` deletes the user's other sessions when `saved_change_to_password_digest?`. The person can also do that deliberately from `/active_sessions`, which lists every `Session` row with its user agent, IP and creation time and offers "revoke this one", "revoke the others" and revoking the current session. Every one of those redirects with `status: :see_other`: without it Turbo re-issues the `DELETE` against the redirect target.

Every sign-in adds a `Session` row, so `/active_sessions` is paginated `ActiveSessionsController::PER_PAGE` at a time (see pagination.md), newest first. The current device can sit on any page. "Revoke the others" shows whenever the user has more than one session in total, read from the paginator's count, because it acts on every page and not only on the one shown.

A session unused for `Session::INACTIVITY_LIMIT` stops working. Resuming a session touches its `updated_at` at most once a day (`Session#record_activity`), so `updated_at` is the last day of use without a write on every request. `find_session_by_cookie` destroys an inactive session instead of resuming it, which signs that device out even before the daily `Session.purge_inactive` in `config/recurring.yml` deletes it. `/active_sessions` states the rule from the same constant.

The purge finds its rows through the `sessions` index on `updated_at`. Without it the daily delete scans every session of every person: about 9 ms at 200,000 sessions against 0.4 ms with it, growing with the table. `test/models/session_test.rb` asserts the query plan.

Account deletion is real erasure and is double-gated. The "Danger zone" card at the bottom of `app/views/profiles/edit.html.erb` posts `DELETE /registration` to `RegistrationsController#destroy`, which requires both the exact locale phrase `registrations.destroy.confirmation_phrase` (shown verbatim in the view) and the account password; a wrong phrase or a wrong password redirects back with `registrations.destroy.error` and deletes nothing. On success `User#request_deletion!` stamps `deletion_requested_at`, deletes every session of the account and enqueues `AccountDeletionJob`; the request terminates its own session and redirects to sign-in at once. The job runs `destroy!`, which cascades sessions, chats, documents, feedbacks, notifications and analytics visits through the `dependent: :destroy` declarations on `User` and purges the avatar. That cascade does not reach RailsPress author records: an app that turns RailsPress authors on has to decide whether a deleted user's posts nullify or destroy.

The erasure runs in a job because it grows with the account's history: each message costs about five queries in RubyLLM's own cascade, so an account with 1,000 messages takes seconds and one with tens of thousands outlives the request timeout. Until the job finishes, `SessionsController#create` refuses the account with the same alert as wrong credentials. `AccountDeletionJob` retries with `retry_on`, and it declares `discard_on ActiveJob::DeserializationError` again after it: handlers declared later win, so without that line the inherited discard would lose to the retry and a job for an account already gone would retry five times. A job that still fails leaves the request stamped, and `User.finish_requested_deletions`, hourly from `config/recurring.yml`, erases every account whose request is older than `User::DELETION_SWEEP_DELAY`.

Both account purges read partial indexes that hold only the rows they look for: `index_users_unconfirmed` and `index_users_deletion_requested`. Each indexes `id`, not the date it filters on, because `find_each` reads in `id` order and SQLite then walks the whole table in `id` order rather than use a date index. Without them every run scans every account; `test/models/user_test.rb` asserts the plan of the query `find_each` really sends.

Two-factor authentication is an extension of these controllers, not a gem to install. The minimal path uses rotp: `otp_secret` and `otp_required_for_login` columns on `users`, and in `SessionsController#create` a redirect to a small verification step, which checks `ROTP::TOTP.new(user.otp_secret).verify(code)`, whenever the user requires it. That step runs before `start_new_session_for(user)`, so a correct password alone never finishes signing in to an account with 2FA. An `otp_secret` is a secret the app holds, so it joins `EXCLUDED_COLUMNS` in the data export (see data-export.md).
