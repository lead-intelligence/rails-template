# Support chat

A floating "Support" button, rendered from the layout for signed-in people by `app/views/support_chats/_widget.html.erb`, opens a dialog holding a Turbo Frame. The frame lands on `SupportChatsController#index`, which offers to start a new conversation and lists the person's recent ones; starting one creates a `Chat` with `support: true` and shows it. Support chats are separate conversations, not one perpetual thread, and they are excluded from `/chats` by the `support` flag.

The list names each conversation by its first question, which the `Chat.with_first_question` scope selects as a correlated subquery. Loading `messages` for the list instead reads the whole history of every listed conversation to show one line of each.

**The binding rule, from the product owner, is that nothing technical may ever reach the person.** No code, no file names, no stack traces, no class names. It is enforced in three independent places, because a prompt alone is not enforcement: `SupportContext::BINDING_RULE` (`app/models/support_context.rb`) states it in the system prompt of every support conversation; `config/support_context.md`, the only app-specific knowledge the assistant gets, is human-friendly by convention and ships as a guided placeholder; and `Message#to_partial_path` renders system, tool-call and tool-result messages as a blank partial in support chats specifically, so even a leaked tool call never reaches the UI. Normal chats still render those in full, for transparency. The data export applies the same rule in SQL through `Message.visible_to_person` (see `data-export.md`), so a downloaded ZIP cannot show what the UI hides; a change to one of the two rules must reach the other.

`SupportAgent` (`app/agents/support_agent.rb`) is a `RubyLLM::Agent` declaring the chat model, the instructions and its tools; the `chat` available inside the tools block is the runtime conversation record, which is why the tool receives the whole chat rather than just its user. `ChatResponseJob` resolves the conversation through `SupportAgent.find` instead of `Chat.find` only when the chat is a support one. The agent applies its instructions without persisting them, so they are injected into the in-memory conversation sent to the provider on every turn and never written as a message row — repeated lookups across a long conversation can therefore neither duplicate nor stale the system message.

`CreateSupportTicketTool` (`app/tools/create_support_ticket_tool.rb`) files the refined ticket as a `Feedback` for the chat's user, reusing the feedback pipeline untouched, including the optional GitHub mirror. The ticket itself can be as technical as it likes — it is for the developer, not for the person. The assistant needs `OPENAI_API_KEY` to reply at all; GitHub forwarding is independently optional.

The widget's Stimulus controller (`app/javascript/controllers/support_chat_controller.js`) captures the page URL, user agent and viewport when it first opens and passes them as parameters into the frame. `SupportChatsController` permits exactly those three keys under `context`, so a `context` sent as a plain string is ignored rather than raising, strips newlines and truncates each to `CONTEXT_VALUE_LIMIT` before storing them as plain, never-interpreted text. The column is `ticket_context` and **must not** be called `context`: RubyLLM's `acts_as_chat` already defines a `context` accessor for provider request configuration, and a same-named column silently shadows it — reads return the gem's object and the next save raises inside the gem's model resolution. `Feedback#context` has no such conflict and is where the tool copies it, and the feedback job renders it in the developer-only part of the issue body.

The paperclip control uploads immediately to `SupportChatPhotosController`, which finds the conversation through `Current.user.chats.support`, so no cross-user attachment is possible, and attaches to `Chat#pending_photos` with the same validations as feedback photos. When a ticket is filed the tool attaches those blobs to the `Feedback` and calls `detach` on the pending ones — never `purge`. Purging a blob a `Feedback` still references would in practice be stopped by the foreign key and rescued by Active Storage, but depending on that rescue for correctness is fragile, because foreign-key enforcement is an environment detail. `detach` removes only the join row and never touches the blob.

A conversation holds at most `Chat::MAX_PENDING_PHOTOS` pending photos, enforced by the `limit` validation and stated to the person through `support_chat_photos.create.too_many`, interpolated from the same constant. `SupportChatPhotosController` refuses uploads to a closed conversation with `403`, like `MessagesController`.

Closing a conversation deletes the photos it never filed. `Chat#close!` detaches the pending photos first and then calls `purge_later` only on blobs in `ActiveStorage::Blob.unattached`, so a blob a `Feedback` still references is never purged, for the same reason the ticket tool detaches. Without it every photo uploaded to a conversation that filed nothing stays in storage forever.

A conversation closes and becomes read-only. `Chat#close!` is idempotent and `Chat#closed?` reads `closed_at`. Two things close one: inactivity, through `Chat.close_inactive_support_conversations` running hourly from `config/recurring.yml`, whose `Chat.inactive` scope compares the last message's timestamp — or the chat's own, if there are none — against `Chat::INACTIVITY_WINDOW` in one query for every open conversation; and resolution, because `Feedback#resolve!` closes the conversation the ticket came from. A closed conversation renders its history with no composer and offers to start another, and `MessagesController`'s `before_action :ensure_open` refuses posts to it with `403`. Hiding the form is not the enforcement. The person never closes anything: they start a new conversation, which is how professional support works, minus the intermediate reopenable state.
